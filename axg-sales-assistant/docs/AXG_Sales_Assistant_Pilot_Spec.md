# Allied Instrumentation — AI Sales Assistant
## Pilot Specification (Internal Build)

**Status:** Draft for internal review — updated to reflect the structured assets now built.
**Scope of this document:** One product family (Yokogawa ADMAG TI AXG magnetic flowmeter), proving the end-to-end concept before any catalog-wide expansion.
**Audience:** Internal build team. Assumes Allied product knowledge.

**Companion artifacts (already built):**
- `axg_model_code.json` — the configurator truth layer: 16 positions, cross-position rules, Allied house defaults, and signal-cable companion logic.
- `axg_dimensions_retrofit.json` — lay-length lookup + competitor retrofit advisor with fit-verdict logic.
- `axg_application_rules.json` — application/tribal-knowledge base: conductivity, grounding, and the chemical-compatibility-at-temperature gate.
- `AXG_Verification_Checklist.md` — the consolidated list of every item still to verify, decide, or capture.

---

## 1. Problem

Sales inquiries arrive as freeform emails describing an application in plain language ("need a 3-inch explosion-proof mag, flanged, HART"). Turning those into a valid Yokogawa model code today is manual: someone interprets the request, cross-references the datasheet, fills in Allied's usual selections, checks which options can legally combine, and writes back asking for whatever is missing. It is slow, depends on individual experience, and a single wrong character in a model code ships the wrong instrument.

The goal is an assistant that reads an inbound inquiry, extracts the spec, fills in what Allied knows, validates the combination, drafts the model code, and produces a short list of the questions still genuinely open — leaving a human to review and send.

---

## 2. Core Architecture Principle (Non-Negotiable)

The system is built as **two strictly separated layers**:

- **Language layer (the LLM).** Reads messy emails, maps plain English onto the product taxonomy, identifies what is missing, asks sensible questions, and writes the reply. This is what a language model is genuinely good at.
- **Truth layer (structured data + deterministic rules).** Holds the model-code positions, allowed values, cross-position rules, dimensions, and Allied defaults. The model code is **assembled and validated by code, never generated by the LLM from memory.**

**The hard rule:** model codes, dimensions, ratings, and material/option compatibility are *looked up and computed*, never free-typed by the language model. If a model hallucinates one digit, we ship the wrong unit. The LLM collects inputs and explains results; it does not invent facts.

This single separation is what makes the system trustworthy enough to put in front of customers.

**Language-layer boundaries (the two LLM touchpoints).** The model does exactly two things, both phrasing not deciding: (1) reading inbound emails into structured fields, and (2) writing the outbound reply from a structured packet. It never produces a model code, dimension, rating, or compatibility verdict. The reply-writer is constrained to convey the facts the engine passes in — it phrases, reorders, and sets tone, but the code, dimensions, flags, and escalations are fixed content it must carry, never generate.

---

## 3. Pilot Scope

**In scope:**
- A single product family: AXG magnetic flowmeter (primary variant table — general-purpose / submersible / explosion-protection, wafer/flange, PFA lining, 2.5–400 mm).
- A deterministic configurator that assembles and validates a model code from selected options, including signal-cable companion items for remote-sensor builds.
- Email intake: extract a structured spec from an inbound inquiry.
- Draft reply: proposed model code, the spec as understood, and the open questions.
- Allied house defaults applied automatically, with the ability to deviate (see §6).
- **Dimensional lookup + retrofit advisor** (built): lay lengths, and competitor cross-reference that tells a customer whether an AXG drops into an existing spool.
- **Application-suitability checks** (built): conductivity floors, grounding logic, and the chemical-compatibility-at-temperature gate.

**Explicitly out of scope for the pilot:**
- Pricing and quotes.
- Other product families (added only after the pattern is proven here).
- Autonomous sending — every reply is human-reviewed.
- Installation documentation (terminal wiring, cable cross-sections) — captured-for-later, not quoting logic.
- Hazardous-area / application-suitability *sign-off* — the agent checks and flags, but a human signs off.

---

## 4. Human-in-the-Loop (Hard Requirement)

The agent **drafts; a person reviews and sends.** This is the liability firewall and it is a requirement, not a phase-one convenience. Application recommendations — anything pressure-, material-, or hazardous-area-related — are always confirmed by a human before going to a customer. The pilot is explicitly *not* targeting autonomous operation.

A useful side effect: every human review generates a labeled example (was the draft right?) that becomes the dataset for measuring accuracy over time.

---

## 5. Functional Requirements

**5.1 Email ingestion & extraction**
- Accept an inbound email (monitored inbox or forwarded address).
- Extract a structured spec object: product family, size, process connection type, explosion-protection need, output/communication protocol, material cues, quantity, and any application context (fluid, pressure, area classification).
- Output structured data, not prose.

**5.2 Gap analysis & question generation**
- Compare the extracted spec against the positions required to complete a valid AXG code.
- Generate questions *only* for what is genuinely missing or ambiguous after defaults are applied — do not re-ask what the customer already stated.

**5.3 Model code generation (deterministic configurator)**
- Assemble the 16-position code from gathered inputs + applied defaults.
- Validate against cross-position rules; reject or flag illegal combinations.
- Never output a code that violates a hard rule.

**5.4 Selection & deviation logic** — see §6.

**5.5 Draft reply assembly**
- Produce: the spec as understood, the proposed model code (with a plain-English breakdown), and the short open-question list.
- Surface any warnings (suboptimal-but-legal choices) and any unresolved data-verification flags.

---

## 6. Selection & Deviation Logic

Precedence for filling each position:

1. **Explicit customer request** — always wins.
2. **Allied house default** — fills any position the customer left silent.
3. **Prompt the user** — if neither applies and the position is required.

Three kinds of deviation, handled differently:

- **Deviation to another valid option** (e.g. `AA1` → `AA2`): free. The agent simply uses it.
- **Deviation to an illegal combination** (e.g. a connection unavailable in the requested size): **blocked.** The agent does not silently comply or silently refuse — it surfaces the conflict and offers the legal alternatives.
- **Deviation to a legal-but-inadvisable choice** (e.g. a material poorly suited to the fluid, or a long-lead combination): **allowed with a warning.** The agent lets it through but flags it for the customer and reviewer.

**Defaults are soft. Validation rules are hard.** Deviate from defaults freely; never deviate from validation rules — surface them instead.

**Fail-safe defaults (override-only).** Some defaults are safety-directional and must not be inferred away by the agent. The Use/Explosion default is `-C` / `A` / `FF2` (explosion-proof) and is **override-only**: an explosion-proof unit is safe in any area, but a general-purpose unit in a classified area is a code violation and hazard — the failure is one-directional. The agent holds `-C` until *explicitly* instructed otherwise (customer states general-purpose, or a reviewer changes it) and asks to confirm the area rather than inferring it. Deciding an area is non-hazardous is a human call, not an agent inference.

## 7. Truth Layer / Data Model

The truth layer spans four files, each a distinct concern:

**`axg_model_code.json` — the configurator.**
- `positions` — the 16 ordered positions, each with allowed codes and plain-English descriptions.
- `cross_position_rules` — the interlocks (remote-sensor positions force blanks; HART excludes the fieldbus-only explosion code; process connections are size-restricted).
- `allied_defaults` — Allied's house selections, each tagged with `source` (`"Allied standard"` vs `"assumed — confirm"`) so defaults are never mistaken for hard rules.
- `companion_items` — non-model-code items that must ship with the order, driven by the model code (the AX01C signal cable for remote-sensor builds, with the transmitter-specific max length).

**`axg_dimensions_retrofit.json` — fitment + retrofit.**
- Yokogawa lay lengths (wafer to 8", flanged to 20", with the wafer-over-8"-doesn't-exist ceiling encoded).
- Competitor cross-reference + `fit_verdict_logic` (drop-in / spool-too-short / needs-spacer) and `retrofit_rules` (e.g. the Rosemount 10"/12" short-spool flag).

**`axg_application_rules.json` — application / tribal knowledge**, in five buckets: disqualifying questions, application rules, never-order list, fluid-to-material, and red flags. Contains the **mandatory chemical-compatibility-at-temperature gate** (see §8).

**`verify` flags** run through all files — fields transcribed from a scrambled PDF that must be confirmed against the clean datasheet before production. All are consolidated in `AXG_Verification_Checklist.md`.

Captured Allied defaults to date: `FF2` (FM flameproof), `AA1` wafer / `BA1` flange (ASME 150), `L` (316L electrode), `2` + `/GRL` (grounding rings, 316L), `JA` (HART 7 + Type A I/O).

---

## 8. Escalation Behavior

When a request falls outside what the knowledge base clearly covers — an unfamiliar application, a combination the data can't validate, anything safety-sensitive — the agent **flags and hands off to a human rather than guessing.** "I'm not sure" is an acceptable and expected output. Confident wrong answers are the failure mode we are explicitly designing against.

**Highest-stakes escalation — the chemical-compatibility gate.** When a fluid is named, the agent must check every wetted part (electrode, lining, grounding ring) against that chemical *at the stated process temperature*, resolving against a **verified compatibility reference — never the model's own memory.** Missing temperature is a required question, not an assumption. Marginal or unverified compatibility escalates to a human. This is the one place where a wrong answer leaks a hazardous chemical rather than producing a bad reading, so it gets the strictest treatment in the system. **Build note:** wiring this gate to let the LLM judge compatibility from memory would be the single most dangerous error in the project — it must call out to a real resistance source.

---

## 9. Prerequisites (The Real Work)

These are deliverables, not afterthoughts. Most of the effort lives here, not in the AI. **All specific items are itemized in `AXG_Verification_Checklist.md`;** the summary:

1. **Verify the flagged data** (checklist sections A–B). Confirm every `verify`-flagged field against the clean datasheet — primarily the process-connection size matrix, the flanged lay lengths, and `GRL`-with-explosion-protection. Use clean datasheet images, not the scrambled text. Estimate: ~1 day per variant table.
2. **Set the business judgments** (checklist section C–D). Fit-verdict tolerances, the low-conductivity band, the assumed defaults, and the verified chemical-resistance source the compatibility gate resolves against.
3. **Capture remaining tribal knowledge** (checklist section E). Chemical-to-material mappings (highest value), the never-order list, and the remaining always-ask questions and red flags.
4. **Assemble a validation set.** Collect 15–20 historically quoted AXG codes (known-correct) and 10 real past inquiry emails for acceptance testing.

---

## 10. Acceptance Criteria

The pilot is successful when:

- **Configurator correctness:** reproduces ≥ 20 historically-quoted AXG codes exactly from their known inputs.
- **Rule enforcement:** correctly rejects or flags illegal combinations (e.g. wafer code in an unsupported size; fieldbus explosion code on a HART build) rather than emitting them.
- **Default application:** correctly fills silent positions with Allied defaults and labels them as defaults.
- **Deviation handling:** handles all three deviation cases correctly (free / blocked-with-alternatives / allowed-with-warning).
- **Email extraction:** from 10 real past inquiry emails, produces a sensible structured spec and a reasonable open-question list, judged by a salesperson.
- **Escalation:** flags out-of-scope requests instead of guessing.

---

## 11. Suggested Build Sequence

- **Phase 0 — Data prep.** Complete §9. No AI yet.
- **Phase 1 — Configurator (deterministic, no LLM).** Build and validate code assembly + rule enforcement against the known-correct set. This is the trust foundation.
- **Phase 2 — Email extraction (LLM).** Add the language layer to produce structured specs from emails.
- **Phase 3 — Draft assembly.** Combine: email in → spec + code + questions out, human-reviewed.
- **Phase 4 — Expand.** Add the next family by repeating the §9/§7 motion. Expansion is grunt work, not reinvention.

Human-in-the-loop applies from the first day the system touches a real customer email.

---

## 12. Key Risks

- **Data quality:** the `verify`-flagged fields are the highest-risk content; a wrong size range produces an unbuildable quote. Mitigation: §9.1, and the configurator refusing to emit unvalidated combinations.
- **Tribal-knowledge gap:** the datasheet says what's *available*, not what's *appropriate*. Mitigation: §9.2 and the warning layer (§6).
- **Scope creep:** the urge to do the whole catalog at once. Mitigation: one family, fully, first.
- **Over-trusting the LLM:** any drift of code/dimension generation into the language layer reintroduces hallucination risk. Mitigation: the §2 separation, enforced in code.

---

## 13. Notes Deliberately Left Open

Tech stack, hosting, and specific LLM/provider choices are intentionally unspecified — they should follow from the pilot, not constrain it. The only firm architectural commitment is the §2 two-layer separation. Keep the structured data in a simple, human-inspectable form (the current JSON is fine) while it is still settling; formalize storage later.

## 14. Scaling to Multiple Instruments (Platform Architecture)

The AXG pilot is instrument #1. The point of the pilot is not the mag meter — it is to prove a pattern that the rest of the catalog can pour into without the trustworthiness degrading. This section captures the architecture that makes that possible. It is forward-looking; the pilot does not build all of it, but the pilot's data should be shaped so this is a natural extension rather than a rewrite.

### 14.1 The load-bearing split: engine vs. content

Every part of the system is one of two things, and they must stay strictly separate:

- **Engine (write-once, instrument-agnostic).** The configurator logic (assemble positions, enforce interlocks, apply defaults with customer > default > ask precedence), the gate framework (ask → look up verified answer → proceed/warn/escalate), the deviation logic (free / blocked / warning), the part-number formatter, the email extraction, and the reply-and-breakdown generator. None of this knows it is a mag meter. It operates on a schema.
- **Content (per instrument).** Everything in the JSON files: positions, allowed codes, cross-position rules, dimensions, house defaults, application rules, optional codes. This is the instrument's "personality."

A new instrument is **new content poured into the same proven engine** — a data-entry-and-verify job, not an engineering project. If engine and content ever blur together, every instrument becomes a rebuild and every rebuild is a fresh chance to introduce errors. Keeping them separate is the whole architecture.

### 14.2 The instrument schema is the real deliverable

The most important artifact to build next is not a second instrument — it is the **schema**: the fixed contract every instrument's data file must satisfy (an instrument has positions; a position has allowed values; values carry restrictions; cross-position rules of defined types; gates of defined types; defaults with source tags). The AXG JSON already reverse-engineers ~80% of this contract. The second instrument is what *proves* the schema and exposes where the AXG's structure was secretly AXG-specific.

### 14.3 Modular capabilities

Instruments are not all shaped alike, so the schema is a **core plus optional capability modules** an instrument declares:

- **Core (every instrument):** positions, defaults, optional codes, explosion/restriction logic, the wetted-materials compatibility gate, part-number assembly.
- **Capability modules (declared as needed):** dimensions/retrofit (AXG), flow-velocity sizing (AXG, vortex), range/span & turndown (pressure, DP), sensor-input matching (temperature), and so on.

The engine loads only the modules an instrument declares — so a thermowell isn't carrying the mag meter's retrofit advisor, and a second flow instrument *reuses* the velocity module wholesale.

### 14.4 Hallucination defense, made structural

The two-layer principle (§2) is the defense, enforced architecturally rather than by discipline:

1. **The model never generates a fact** — not a code, dimension, or compatibility verdict. The engine hands the LLM a structured packet; the prompt is constrained to "convey exactly these facts." Even a hallucinating model has nothing to invent because the facts are passed in, not asked for. This applies to the **reply-writing** step as much as anywhere: the LLM phrases the facts, never produces them.
2. **Provenance on every datum.** Every value carries where it came from and whether it is confirmed (the existing `status: verified` / `source: Allied standard` tags, made mandatory in the schema). The engine **refuses to put an unverified value into a customer-facing part number** — it escalates instead, exactly like the provisional electrode. A half-built instrument therefore *cannot* produce a confident wrong quote; the worst it does is say "routing to a human." Hallucination becomes structurally impossible, not because the model is careful, but because unverified data is quarantined.

### 14.5 Shared cross-instrument services

Some content is universal and must be built **once, centrally**, not re-entered per instrument:

- **Material compatibility / chemical-resistance reference** (316L vs. nitric acid at 80 °C is the same answer on any instrument).
- **Yokogawa explosion-protection certification codes** (FF2 and the ATEX/IECEx/FM apparatus are largely common across the EJA, VY, YTA, and AXG families).
- **Unit conversions, ASME flange pressure ratings, area-classification logic.**

Every instrument's gates reference these shared services. This is where the per-instrument cost curve bends down — instrument three is cheaper than instrument two.

### 14.6 Confirmed near-term instruments and build sequence

All Yokogawa, all suffix-code instruments in the same GS-document format as the AXG — i.e. the *same schema, repeated*, not four different shapes:

| Order | Instrument | Base code | Proves | New module(s) |
|---|---|---|---|---|
| 1 | Mag meter (pilot) | AXG | the pattern | dimensions/retrofit, velocity sizing |
| 2 | Pressure transmitter | EJA530E | near-copy reuse (closest twin to AXG) | range / span / turndown |
| 3 | DP transmitter | EJA110E | family reuse (same EJA-E family) | manifold / impulse-line content |
| 4 | Vortex meter | VY | module reuse (reuses velocity sizing) | low-flow / Reynolds cutoff |
| 5 | Temperature transmitter | YTA610 + RE OTEMP well + element | multi-vendor assembly + cross-item rules | sensor-input matching, assembly wrapper |

The sequence is chosen so each instrument stress-tests a different property of the architecture, not by difficulty. Pressure (EJA530E) is second because it is the closest structural twin to the AXG and most of it transfers straight to the DP. Temperature is last because it is the structural outlier — a three-item, two-vendor assembly (see 14.7) — and proves the assembly/cross-item-rules concept that simpler linked cases reuse.

### 14.7 Linked model codes & multi-vendor assemblies (CONFIRMED REQUIREMENT)

Some quotes are not one part number but an **assembly of linked items**, sometimes across vendors. This is now a confirmed, first-class schema primitive — not deferred. The pattern already appears in the pilot (a remote-sensor AXG needs the AX01C signal cable) and is fullest for temperature.

**Temperature is a three-item, two-vendor assembly.** A single temperature point resolves to three separate part numbers:

1. **Yokogawa `YTA610`** — the transmitter (no process contact).
2. **RE OTEMP thermowell** — standardized vendor; the **only wetted part**.
3. **RE OTEMP element** — RTD (typically Pt100) or thermocouple; a *separate* RE OTEMP part number from the well.

RE OTEMP is the standardized thermowell + element vendor. Their products are configured/ordered (stem style, length, material, connection, element type as selectable options), so they conform to the same suffix-code schema as the AXG — encoding them is a normal content-build from RE OTEMP datasheets, **done from their published config data, never from model memory.**

**The new module temperature introduces is cross-ITEM rules** (the AXG had cross-*position* rules within one code; this spans items, across vendors). The engine must validate, before any of it reaches the customer:

- **Element ↔ transmitter:** the RE OTEMP element type (RTD vs. TC, and which) must match the YTA610 input configuration.
- **Element ↔ thermowell:** element diameter/length must fit the thermowell bore and "U" length (insertion depth).
- **Thermowell ↔ process:** well connection, rating, and stem length must suit the line; **the thermowell material must clear the shared compatibility gate** — it is the wetted part, so the chemical-resistance logic applies to the RE OTEMP well, not the Yokogawa transmitter or the element.

**The quote output** lists three part numbers under one assembly, each with its own plain-English breakdown and ERP part number, and the engine confirms the three agree before drafting. A mismatch (e.g. TC element + RTD-configured transmitter, or an element too large for the well bore) is a blocked combination surfaced to the reviewer, exactly like an illegal within-code combination.

**Schema impact:** add an **"assembly" wrapper** holding N schema-conforming items (possibly multi-vendor), plus a **cross-item rules** module. Add **RE OTEMP** as a known vendor alongside Yokogawa. Once the schema handles three linked codes across two vendors, simpler linked cases (remote-sensor AXG + cable, DP + manifold) are trivial subsets.

## 15. Routing & Extensibility Contract (How New Things Get Added)

This section exists to answer one concern directly: **don't build so far down the instrument road that valves (or anything unlike a transmitter) can't be added without a rewrite.** The protection is not "build everything now" — it is a clean contract for how any new instrument plugs in, plus one specific seam (the result shape) kept general from the start.

### 15.1 Parsing is routing-then-extraction, not extract-then-classify

Different instruments share almost no fields (a valve has Cv/trim/actuator; a pressure transmitter has span/capsule/wetted parts). So you cannot "extract properly" before knowing what the document is. Parsing therefore runs as **two coarse routing passes, then specialized extraction**:

1. **Input-type router (universal):** what *format* is this — pasted text, image, or PDF? Text → straight to extraction. Image → vision read. PDF → text-extract → markdown (visible, checkable) → extraction. (See §16 / PDF tooling.)
2. **Instrument triage (universal, coarse):** what *kind of instrument* is this — flow, pressure, valve, …, or unrecognized? This is a shallow classification from a few signals (element type, model prefix, "Cv", manufacturer), NOT full extraction. It must include "unrecognized."
3. **Specialized extraction (per-instrument):** now that the kind is known, run that instrument's own extractor, which knows only its fields and validates against its own schema.
4. **Engine (per-instrument):** the matching engine produces the result.

The only must-handle-everything components are the two routers. Everything downstream is specialized and self-contained.

### 15.2 Triage rule: recognize confidently, decline humbly

Triage must be biased toward **declining when unsure** rather than guessing. "I think this is a valve — confirm?" is safe; silently routing a valve to a flow extractor is the dangerous failure (it produces a plausible wrong answer). An unrecognized or out-of-scope document (e.g. a control valve today) must be **recognized and declined cleanly** — "this is a control valve, not something I quote yet" — never forced into the nearest existing schema. The schema-recognition layer already does this (it correctly declined a B&V control-valve datasheet). Graceful decline on out-of-scope input is a required feature, not a gap.

**Start with user-confirmed routing, earn auto-classification.** For a single expert user, the most reliable triage is to let the user confirm the instrument type (a pick list), and offer auto-classification only as a *suggestion the user confirms*. Add fuller auto-triage once enough real documents prove it reliable. This avoids auto-classification's silent-misroute risk before the convenience is needed.

### 15.3 The extensibility contract (what "an instrument" is)

An instrument is a self-contained bundle of four things, plugged in behind the routers:

- **a schema** (its positions/fields and valid values),
- **an extractor** (pulls its fields from a document; knows only its own fields),
- **an engine** (applies defaults, rules, gates; produces a result),
- **declared capability modules** (see §14.3 — e.g. velocity-sizing, range/span, Cv-sizing, multi-component-assembly).

**Adding an instrument touches none of the others.** A new instrument is a new bundle registered with the triage router; existing instruments never see its documents and are not modified. This is the property that keeps the blast radius of "add a thing" tiny, and it is already how AXG and EJA coexist.

### 15.4 The result contract (the seam that protects valve-ability)

This is the one place a transmitter-only assumption could quietly lock out valves, so it is fixed deliberately. Every engine returns a **normalized result** the renderer can draw. Today that result is dominated by a suffix code. The contract requires the result shape to also be able to carry:

- **a suffix/model code** (transmitters, vortex) — the common case;
- **a computed sizing outcome** that is NOT a code position (e.g. a vortex Reynolds/low-flow verdict; a valve Cv and predicted noise) — a pass/fail/number the engine *calculated*, not selected;
- **a multi-component assembly** (N linked items, possibly multi-vendor — the temperature transmitter + thermowell + element; eventually valve body + actuator + positioner);
- **gates, flags, open questions, provisional markers** (already general).

A result may use any subset. A transmitter uses code + gates. A valve, when built, uses computed-sizing + assembly + gates — and the renderer/contract already accommodate it.

**The vortex is the cheap in-family test of this seam.** The vortex introduces a *computed* result (the Reynolds/velocity floor) that is not a code position — the first result that isn't "just a code." If the vortex's computed-sizing verdict flows through the result contract cleanly, that is real evidence the contract can later carry a valve's Cv result. If it strains, the weakness is found now, on a cheap in-family instrument, not later when valves are actually needed. **Design the vortex result to exercise computed-sizing explicitly**, so building it doubles as proving the seam.

### 15.5 What this does and does not commit to

This contract makes valves (and other non-transmitter instruments) **addable later without a rewrite** — it does NOT build them now. Build order stays in-family (vortex → finish EJA → temperature assembly); each compounds on the shared engine. Valves remain recognized-and-declined until deliberately built. The cost of preserving valve-ability is small and paid here: the routing shape, the decline-when-unsure rule, the four-part instrument bundle, and a result contract that can express computed/assembly outputs — not just suffix codes.
